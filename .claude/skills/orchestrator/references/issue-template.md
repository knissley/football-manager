# The standard issue body

Every issue the orchestrator runs has this shape. The designer files them from a data file
rendered to a review page first, so the owner reads the whole set before any is filed. The
labels and their meaning are the `/orchestrator` skill's state machine; this file is only
the body.

**Title:** `[<ID>] <the football sentence>` where the ID is a track letter and a number
(`A1`, `C14`). The title says what will be true when it is done, not what is wrong.

**Labels:** the backlog's label (`audit-backlog` today, or the milestone's), `track:<letter>`,
`wave:<n>`, and exactly one `status:` (`ready` or `blocked` at filing). `needs-owner` is a
flag, not a status: an issue waiting on a decision carries it and `status:blocked` both.

```
**Track:** <track name> · **Wave:** <n> · **Size:** small | medium | large
**Depends on:** none | #<n> (<ID>), ...
**Tracker:** #<tracker>
**Found by:** <the review, audit or brief, with the commit and date>
**Where it fits:** <the batch it lands in; what it must follow or precede, and why>

## Problem

<What is wrong, measured, with the numbers and where they came from. Cite the sport.>

## Plan

1. <Steps an agent can execute without asking. Name files and types.>

## Done when

- [ ] <Checkable statements. A harness row, a test, a printed game.>

## Files

`<path>`, `<path>`

---

## Conventions

<the conventions block, verbatim from CLAUDE.md's "Current work" section>

---
_Generated by [Claude Code](https://claude.ai/code)_
```

## Waves and tracks

- A **track** groups issues by the part of the system they change; one letter each.
- A **wave** groups issues by when they can land. Wave 0 changes no engine behaviour and
  runs in parallel. Every later wave regenerates goldens and lands one PR at a time.
- **Depends on** lists issues that must be done first; `status:blocked` until they are.
- **Where it fits** is the sentence the orchestrator reads when inserting the issue into
  a running chain.

## The tracker issue

Title `<milestone or backlog> tracker`, label `tracker`. **The body is the state and the
comments are history**, as the `/orchestrator` skill says. Body, in order: a *Current state*
section at the top, rewritten in place (`main` sha, counts, what is in flight, what waits on
the owner, the queue); what the backlog is for; how it is organised (the backlog label,
waves, batching, the integration branch); the reading order for a fresh session; a tracks
list; the waves table as filed, with the notes beneath it that labels cannot recover; the
gates the owner releases by hand. Comments carry wave summaries, residuals reported to the
retune, corrections and standing-rule changes, never a description of where things stand.

## Filing

Keep the issues in one data file (`issues.py` with `ISSUES`, `WAVES`, `TRACKS`,
`CONVENTIONS`), render a review page from it, and file from the same file so the page and
the issues cannot differ. File in dependency order so `Depends on` can cite numbers.
Record ID-to-number in a JSON file and fill the tracker's waves table from it.
